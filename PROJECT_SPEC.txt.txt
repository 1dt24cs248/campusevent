PART 1 - PRODUCT SUMMARY AND NON-NEGOTIABLE RULES
--------------------------------------------------------------------------
Students, faculty and management use ONE connected platform on ONE shared campus data model. The main innovation: management can ask "What happens if I make this decision?" BEFORE doing it. The system simulates the decision on a temporary copy of the campus state, finds affected classes/sections/faculty, searches alternative rooms with a constraint optimizer, produces up to 3 distinct options with impact metrics, lets management compare scenarios, and only after human approval publishes the change to faculty, students, navigation and the AI assistant.

The product is NOT: a timetable generator, a room-booking app, a generic ERP, or a ChatGPT clone.

NON-NEGOTIABLE RULES
R1  The LLM never decides room allocation. Flow is always: natural language -> AI interpretation -> structured scenario -> OR-Tools CP-SAT optimizer -> result -> explanation. Allocation decisions come only from the optimizer.
R2  Never fake feasibility. If rooms/capacity are insufficient, say "No feasible allocation found" (or "Partially feasible") and explain exactly why, with numbers.
R3  A simulation NEVER changes the published campus state. Only "Approve & Publish" by a Management user does.
R4  Three states must stay distinct: (a) current published state, (b) temporary simulated scenario, (c) approved/published new version. Keep version history and support revert.
R5  No fabricated real-world data. Every data record carries a provenance tag: PROVIDED (given by me in this spec), ESTIMATED (placeholder for a value I did not give; editable), SYNTHETIC (generated test data), or REAL_TIMETABLE_PDF (extracted from the real timetable). The UI must show a small provenance chip wherever it matters (rooms, sections, timetable entries) and a legend.
R6  Never claim energy, electricity, money, or food-waste savings. Utilization is computed from timetable data only.
R7  Safety module: never claim guaranteed emergency response. Emergency integrations run in clearly labelled TEST MODE using configurable test contacts.
R8  Sensitive data (incidents) is encrypted at rest and visible only to the Safety role. Every sensitive access is audit-logged.
R9  AI answers only from tool results (campus database). If data is missing the assistant says "That information is not available in the campus data." It never invents rooms, times, reasons, events.
R10 The architecture must allow adding Block B, C... later with no redesign: every room/floor belongs to a Block row; Block A is the only active block and the default selection.

PART 7 - ALLOCATION ENGINE AND OPTIMIZER (THE CORE - BUILD CAREFULLY)
--------------------------------------------------------------------------
7.1 CampusState (engine/state.py): immutable snapshot for a date range = rooms + sessions (template expanded to dates, published overrides applied) + unavailability windows (real, active) + settings. A scenario state = base snapshot + in-memory delta from scenario changes. NEVER write scenario effects to production tables during simulation. (Test this.)

7.2 suitable_rooms(session, state) (engine/candidates.py) returns candidate rooms and, for rejected rooms, the machine-readable rejection reason. Filters:
   - room status ACTIVE and allocatable_for_classes (offices, staff room, meeting hall, common-use excluded unless enabled)
   - type: THEORY -> CLASSROOM or SEMINAR_HALL; LAB -> LAB with matching lab_kind
   - capacity known and >= effective group size (capacity_basis rule); null capacity -> rejected "capacity not provided"
   - required facilities subset of room facilities
   - not overlapping any unavailability window (check every slot of the session by actual times)
   - not occupied by a FIXED session in any covered slot
7.3 Validation of a state (engine/validate.py): classify every session:
   ALLOCATED (valid room), AT_RISK (valid room but fewer than at_risk_min_backups backup candidates free in that slot), FLOATING (no valid room exists for it), NEEDS_REALLOCATION (current room invalid because unavailable/closed/over capacity/conflict, but alternatives exist). Also detect: ROOM_CONFLICT, SECTION_CONFLICT, FACULTY_CONFLICT, CAPACITY_VIOLATION, UNAVAILABLE_ROOM_USED, TYPE_MISMATCH, FACILITY_MISSING. Every finding has a human-readable reason. Produce the summary line, e.g. "3 sections allocated, 1 at risk, 2 rooms unavailable, 1 capacity conflict" - computed, not hard-coded.
7.4 Dynamic backup pool: backup_pool(state, day_key, slot) = rooms that are actually free in that slot (not unavailable, not occupied) and allocatable. A room is a backup CANDIDATE for a specific session only if it also satisfies that session's requirements. Never label a room "backup" statically.
7.5 CP-SAT optimizer (engine/optimizer.py), ortools.sat.python.cp_model:
   Variables: x[s,r] boolean for each free session s and candidate room r; u[s] boolean "unassigned".
   Hard constraints: each free session exactly one of {one room, unassigned}; a room hosts at most one session per (day_key, slot) cell (account for multi-slot lab blocks); candidates already exclude unavailable/unsuitable/fixed-occupied rooms. Faculty/section double-booking is a property of the time layout: validate it (and for MOVE_CLASS changes, reject a move that creates a faculty/section clash and report why).
   Objective (minimize, integers): W_UNASSIGNED*u dominates everything (10000) so the solver always maximizes accommodated classes; plus weighted soft terms per assignment: room change (r != original), walking effort (graph distance original->new), faculty movement (distance to the faculty's adjacent fixed session rooms the same day; simplified linear form, document it), wasted capacity (capacity - group size), department mismatch (small), different floor, and a heavy stability penalty for moving sessions that were NOT directly affected.
   Settings: random_seed fixed, time limit SOLVER_TIME_LIMIT_SEC, deterministic output.
   Free vs fixed: default "local repair": only directly affected sessions are free; all others are fixed. Strategy REBALANCE additionally frees unaffected sessions whose cells overlap the affected cells (high stability penalty) - this can find solutions local repair cannot.
   Return: assignments {session_key: room_id|None}, objective, status, solve ms.
7.6 Strategy presets (weights) -> options (engine/options.py):
   MIN_DISRUPTION (min room changes), MIN_WALKING (min student walking effort), MIN_FACULTY_MOVEMENT, MIN_WASTE (tightest capacity fit), REBALANCE (may move unaffected classes).
   Run presets, de-duplicate by assignment signature, keep up to 3 DISTINCT options. If fewer than 3 distinct and at least one is feasible, add no-good cuts (forbid previous full assignment) and re-solve up to 3 more times to get "next best distinct" options. If fewer distinct solutions exist, say so honestly ("only 2 distinct feasible allocations exist"). Rank by (unresolved asc, room changes asc, walking asc); mark the best "Recommended".
   Option status: FEASIBLE (all affected sessions accommodated), PARTIAL (some unresolved), INFEASIBLE (none accommodated / impossible).
7.7 Impact analysis (engine/impact.py). Compute per option and for the scenario: affected rooms, affected sessions/classes, affected sections, affected faculty, alternative rooms found (distinct rooms usable), room changes, floating/unresolved classes created, conflicts, unaffected classes moved (REBALANCE), walking impact (relative effort units, plus student-weighted = distance x group size; label "relative units, not meters"), faculty movement, capacity waste, utilization before vs after (overall, per floor, per room), overall feasibility. Provide a full diff table: session | section | subject | faculty | time | original room -> new room | reason.
7.8 Explanations (engine/explain.py) - deterministic templates filled with computed facts, e.g. "A201 was selected for 3rd Year CSE-A DBMS (P2, 10:25-11:20) because: capacity 65 >= 63 students; free in P2; type matches; no conflicts; lower walking effort (X units) than A105 (Y units). Rooms rejected: A102 closed by scenario, A104 occupied by 2ME-A, A103 capacity 50 < 63." Include top-3 alternatives with why not chosen. An LLM may OPTIONALLY rephrase; the numbers must come from data, and the original deterministic text stays available.
7.9 Infeasibility handling (engine/recovery.py). For every unresolved session produce: (a) exclusion breakdown (how many rooms were rejected by each rule); (b) shortage statement per time cell: "N classes need suitable rooms at <time> on <date>, but only M suitable rooms are free; N-M remain unallocated"; (c) near-miss rooms ("B04 capacity 55 is 12 seats short"); (d) recovery suggestions computed from data: 1) time shift: slots on the same date where section + faculty are free and a suitable room is free; 2) release reserved room: which closed rooms in the scenario would satisfy the class if released; 3) change requirement (e.g. split section / reduce strength) only when near-miss exists; 4) "use another block" shown only as "No other block enabled in pilot" unless one is active; 5) escalate to management. Never invent a room.
7.10 Initial allocation: seed script runs the optimizer on the template week (day_key = weekday) to produce base_room for each entry (home room soft preference). Must end with zero room conflicts.

PART 8 - SCENARIO SYSTEM (ONE MECHANISM FOR EVERYTHING)
--------------------------------------------------------------------------
All what-if scenarios are lists of typed changes applied to the same state:
  ROOM_UNAVAILABLE {room_ids, date_from, date_to, time_from, time_to, reason_type, label}   (event, maintenance, exam, closure, lab unavailable, seminar hall reserved, single room)
  FLOOR_UNAVAILABLE {floor_id, window}   (expands to all rooms on that floor)
  RESERVE_ROOMS {room_ids, window, label}   (same engine as ROOM_UNAVAILABLE, shown as event/exam reservation)
  CHANGE_STRENGTH {section_id, new_strength, date_from, date_to}
  ADD_SECTION {department, year, name, strength, clone_pattern_from_section_id, date_from, date_to}  (clones a reference section's weekly slot pattern into new entries with no room, so the engine must find rooms; if capacity is insufficient the new section is AT_RISK/FLOATING with a shortage explanation)
  MOVE_CLASS {entry_id, date, new_start_slot}  (check faculty/section clash at the new time; then room search)
  STRESS_TEST {k, window}  helper: closes the k most-occupied allocatable rooms in the window (heuristic, say so; not a worst-case guarantee) to answer "Can all classes be accommodated if five classrooms become unavailable?"
Lifecycle: DRAFT -> SIMULATED -> REVIEWED -> APPROVED -> PUBLISHED (or REJECTED). Show the pipeline in the UI.
Presets (buttons in the simulator): "Hero: College Event" (see PART 17), "Rooms A101-A104 (example from brief)", "Floor 1 closure", "A201 maintenance 3 days", "Lab unavailable", "Seminar hall reserved", "New first-year section", "Strength 63 -> 75", "Move classes", "Stress test: 5 rooms". The preset must create real scenario records you can edit and re-run.
Scenario comparison: select 2-4 scenarios (or options) and show side by side: affected classes, sections, room changes, floating classes, conflicts, alternatives, walking impact, utilization, feasibility; highlight the least disruptive.
Objective preferences exposed to management: min room changes | min floating classes | min walking | min faculty movement | min unused capacity | min disruption | "keep first-year classes unchanged if possible" (implemented as heavy stability penalty on first-year sessions). These are optimizer weights, never an AI choice.
Review actions: Reject, Modify (edit scenario and re-run), Run Again, Approve & Publish.

PUBLISH (engine/publish.py), single DB transaction:
  1. Check scenario.base_version_id == current version; if not, return 409 "Campus state changed since this simulation - re-run."
  2. Write Approval + PublishedVersion(version_no+1).
  3. For each changed session write SessionOverride(version, old_room, new_room, reason=scenario label + cause). Reason text is stored and is the ONLY source the AI may use to explain a change.
  4. Make scenario closures real (RoomUnavailability with version_id) for ROOM/FLOOR/RESERVE changes; apply CHANGE_STRENGTH (history row); create section + entries for ADD_SECTION; create dated overrides for MOVE_CLASS.
  5. Create Notification rows: audience FACULTY(faculty_id) and SECTION(section_id) per affected session, plus ROLE(MANAGEMENT) summary.
  6. Write AuditLog.
  Revert: management can revert a version (deactivate its overrides/unavailabilities, mark reverted, notify again).

PART 9 - CONNECTED WORKFLOW (MUST DEMONSTRABLY WORK)
--------------------------------------------------------------------------
After publish, with NO manual steps: faculty dashboard shows "DBMS -> new room"; student dashboard shows "Room changed: OLD -> NEW" with the stored reason (if the role may see it); Navigation to that class routes to the new room; the AI answers with the new room; management dashboard utilization and room status reflect the new state; unavailable rooms are excluded from future allocation.

  Event created (Events page, reserves rooms) -> RoomUnavailability -> state changes -> validation flags NEEDS_REALLOCATION -> "Check impact" opens a prefilled scenario -> same simulate/approve/publish path.

PART 10 - CAMPUS AI ASSISTANT
--------------------------------------------------------------------------
Endpoint POST /api/ai/chat {message, conversation_id?}. Role-aware. Returns {answer, sources[], tool_calls[], mode: "rule-based"|"llm", scenario_draft?}.
Tools (functions over the DB; authorization enforced INSIDE each tool using the JWT user, not in the prompt):
  get_my_timetable(date), get_next_class(), get_class_room(subject?, date?), where_is_room(code_or_name) (block, floor, type, capacity, current status), list_events(range), list_opportunities(filters), get_next_assessment(), list_announcements(), explain_room_change(subject?, date?) (reads ONLY the stored override reason + scenario label; if none: "No reason was recorded"), search_faq(query), faculty: get_my_schedule(), management only: create_scenario_from_text(text) and get_scenario_summary(id).
There is NO tool that publishes or edits the timetable.
Rule-based router (NullProvider, default, must cover the demo): intent patterns + fuzzy matching for subjects and room codes: "where is my next class", "what classes do I have today/tomorrow", "where is A201", "where is my DBMS class (today)", "why was it changed", "what events this week", "what hackathons are available", "when is my next assessment/internal", "what is my schedule" ; management: natural-language what-if (below).
LLM mode (when LLM_PROVIDER set): function-calling loop over the same tools; system prompt forces: answer only from tool results; say "not available" if absent; never invent; keep short. Send minimum necessary data (no names beyond display_name). On any LLM error fall back to rule-based mode and show a small "offline mode" badge.
NL -> Scenario (nl_scenario.py): parse management text into the structured ScenarioChange JSON validated by Pydantic. LLM mode: JSON-schema output. Fallback parser must handle: room lists/ranges ("A101, A102 and A103", "A101-A106"), floors ("entire 1st floor"), times ("10 AM to 1 PM", "10 to 12"), dates ("today", "tomorrow", weekdays, "for three days"), reasons (event, maintenance, exam), strength changes ("CSE-B from 67 to 75"), counts ("five classrooms" -> STRESS_TEST). Show the interpretation as an editable form ("I understood this as: ...") BEFORE/WITH running the simulation; running a simulation is safe because it changes nothing. After results, the explanation text is generated from computed facts.
UI must show a three-chip "Decision Trace" on scenarios: [AI interpreted] -> [Optimizer computed] -> [Human approved], with timestamps/actors. Responsible-AI badge text: "AI interprets and explains. The optimizer decides. Management approves."

PART 20 - HARD DON'TS
--------------------------------------------------------------------------
- Don't let the LLM choose rooms, publish, or invent campus facts.
- Don't hard-code demo answers, fake metrics, or pre-baked results.
- Don't present estimated/synthetic data as real; don't claim savings, emergency guarantees, or whole-college coverage.
- Don't treat offices, staff rooms, meeting hall or common-use rooms as ordinary classrooms.
- Don't create static "backup rooms"; backups are computed per time slot.
- Don't auto-publish a simulation; don't let simulation touch production tables.
- Don't expose incident content to non-Safety users or send sensitive data to the LLM.
- Don't add features outside this spec (food ordering, push, Docker, microservices).
